> 原则：以"交付物（成果）"作为分解主线，至少分解到三级（L3）；不以"开会、讨论、修改代码"等纯动作作为主线。

## 1. 项目总目标
完成"校园活动报名与签到管理系统"项目管理综合实验涉及的全部交付物，形成可受控、可追溯的项目仓库，并通过 `main` 分支提交最终成果。

## 2. 一级交付物
WBS 一级条目对应"主要成果域"：

1. **项目管理成果**：保证项目过程受控、可追溯。
2. **业务功能成果（设计文档）**：围绕题目业务给出文档化设计成果，不要求实现。
3. **协作过程成果**：体现版本控制、分支协作与冲突处理能力。
4. **总结与归档成果**：保证实验结束时形成可评审的最终材料。

## 4. 分解说明

### 4.1 分解思路
本组在分解时坚持三个原则：

1. **结果导向**：每个三级条目都是一项可识别、可交付、可验收的成果，避免使用"开会""讨论""调整"等动作型语言。
2. **完整覆盖范围**：将题目说明书中明确纳入范围（活动发布、报名、审核、签到、统计、导出）一一对应到 2.x 业务文档成果，确保 WBS 覆盖范围完整。
3. **可独立分配**：三级条目尽量保持单一责任人能在一日之内完成，便于编排进度与组内分工。

### 4.2 分解层级说明
- 一级（L1）对应主要成果域，体现项目整体输出维度。
- 二级（L2）体现该域内的子成果聚类，按交付物类型聚合。
- 三级（L3）为可分配、可验收的最小成果单元，作为进度计划与配置管理的基础。

### 4.3 范围排除项
本 WBS 不包含以下条目，原因为题目说明书中已明确不纳入范围：

- 复杂支付功能、统一身份认证对接、高并发优化与正式部署。
- 移动端 App 完整开发。
- 高保真原型与正式 UI 设计。

### 4.4 与进度计划、配置管理的对应
- WBS 中标注的每个 L3 成果均会在 `docs/03-schedule.md` 中对应到关键活动的"对应交付物"列。
- 每个 L3 成果在 `docs/04-config-plan.md` §1 中纳入配置项管理。
