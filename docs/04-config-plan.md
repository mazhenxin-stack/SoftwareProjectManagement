- 基线建立后，对应配置项的修改必须通过新分支 + Pull Request（或本地合并申请）的方式进行，禁止直接在 `main` 上修改。

## 2. 分支策略

### 2.1 分支模型（GitFlow 简化版）
```
main (受保护，仅存放经过评审的最终版本)
 └── dev (阶段集成分支，所有 feature 分支先合并到此处)
       ├── feature-charter      朱默涵：项目启动说明
       ├── feature-wbs          马振鑫：WBS 文档
       ├── feature-schedule     马振鑫：进度计划
       ├── feature-config       杜航屹：配置管理文档
       └── feature-collab       刘瑞祥：协作完善与冲突处理
```

### 2.2 分支用途说明
| 分支 | 用途 | 创建时机 | 销毁时机 | 允许直接提交 |
|---|---|---|---|---|
| `main` | 存放经过评审的最终版本 | 仓库初始化 | 永久保留 | 否，仅接受合并 |
| `dev` | 集成各 feature 分支、产出阶段性可发布版本 | 仓库初始化后由配置管理员创建 | 永久保留 | 否，仅接受合并 |
| `feature-*` | 单一交付物的开发与编辑 | 由对应责任人按需创建 | 合并入 `dev` 并验证后删除（或保留作为留痕） | 是 |

## 3. 命名约定

### 3.1 文档命名
- 主交付物按 `NN-name.md` 编号（如 `02-wbs.md`），保持顺序与可识别度。
- 临时讨论文档以 `draft-*.md` 命名；正式合并前必须重命名或合并到主交付物。

### 3.2 分支命名
- `feature-<交付物或主题>`，如 `feature-wbs`、`feature-schedule`、`feature-config`、`feature-collab`、`feature-charter`。
- 个人临时分支可使用 `wip/<拼音>/<主题>` 的形式，禁止使用模糊名称如 `tmp`、`test1`。

### 3.3 提交说明（Commit Message）
- 中文 + 必要英文前缀，遵循动宾结构。前缀建议如下：
  - `init:` 仓库初始化或目录结构变更。
  - `docs:` 文档新增或修改。
  - `fix:` 修复内容错误。
  - `merge:` 分支合并。
  - `chore:` 杂项维护。
- 示例：`docs: 完成 WBS 三级分解并补充分解说明`、`fix: 修正进度计划 A3 的前置关系`。

### 3.4 提交人名称
- 所有成员提交时统一使用本人姓名拼音全称作为 `user.name`：

## 4. 合并规则

### 4.1 合并审批
| 目标分支 | 审批人 | 合并方式 | 备注 |
|---|---|---|---|
| `dev` | 配置管理员（杜航屹） | `--no-ff` 显式合并 | 保留分支轨迹，便于事后追溯 |
| `main` | 项目经理（朱默涵） | `--no-ff` 显式合并 | 仅在里程碑完成时执行 |

### 4.2 合并时机
- feature 分支自检完成后即可申请合并到 `dev`。
- `dev` → `main`：仅在里程碑完成且总结报告已通过全员评审后执行。

### 4.3 冲突处理流程
1. 合并前先 `git fetch` 并在本分支上 `git merge dev`（或 `rebase`）以提前发现冲突。
2. 出现冲突时由相关分支责任人协商，原则上保留双方意图，必要时合并表述。
3. 冲突解决后由配置管理员复核，复核无误方可合并。
4. 冲突过程在 `docs/conflict.md` 中以追加记录的方式留档，保留冲突原因、处理方式、最终结论。

## 5. 版本留痕

### 5.1 提交粒度
- 每次提交聚焦"一项可独立说明的改动"，避免一个提交内同时改动多份不相关文档。
- 提交说明包含改动目的、关键变更点；超过 3 行时使用多行 message。

### 5.2 关键节点留痕
- 每个里程碑由配置管理员打 Tag：
  - `v0.M1` 仓库初始化基线；
  - `v0.M2` 范围与进度基线；
  - `v0.M3` 配置管理基线；
  - `v0.M4` 冲突解决基线；
  - `v1.0` 总结报告基线（最终发布）。
- 阶段性合并提交保留分支信息（采用 `--no-ff`）。

### 5.3 历史保护
- `main`、`dev` 分支启用受保护模式，禁止 `force push` 与历史改写。
- 仓库管理员定期备份 `git bundle` 至本地存档，防止远端意外丢失。

## 6. 单人成组冲突演练补充
若小组实际人数不足两人参与冲突演练，可由同一人在 `feature-collab` 与 `feature-charter` 两条分支上分别修改 `docs/conflict.md` 同一行，再切换到 `dev` 执行 `git merge` 制造冲突。本组虽为 4 人，但仍按教师在指导书中提到的冲突制造方式作为对照参考记录在此。
