## 2. WBS 分解思路

### 2.1 一级条目划分理由
本组将项目交付物划分为 4 个一级条目：项目管理成果、业务功能成果（设计文档）、协作过程成果、总结与归档成果。这 4 个一级条目分别对应"过程受控"、"范围覆盖"、"协作能力"和"实验收尾"四个维度，能够把指导书与题目说明书提出的全部要求映射到具体成果上。

### 2.2 三级分解原则
分解中坚持三条原则：

1. **结果导向**：每条 L3 条目都是一项可识别、可交付、可验收的成果，避免使用"开会、讨论、修改"等纯动作型语言。例如 1.2.2 直接对应 `docs/03-schedule.md` 文件，而不是"做进度计划"动作。
2. **范围完整覆盖**：将题目说明书中明确的"活动管理 / 报名管理 / 签到管理 / 统计与导出"4 类业务一一映射到 2.1–2.4 子树，避免漏项；同时把指导书中提到的协作过程成果落到 3.x，把总结归档落到 4.x，与实验报告章节直接对应。
3. **可独立分配**：L3 条目以"一人一日内可完成"为粒度参考，例如 2.1.1 活动信息字段说明与 2.1.2 活动发布页面草案分开作为两条 L3，便于在进度计划中独立排期与分配。

### 2.3 与进度计划、配置管理的对应
WBS 中每条 L3 都在 `docs/03-schedule.md` 的"对应 WBS 成果"列中被明确引用，并在 `docs/04-config-plan.md` §1 的配置项清单中作为受控对象进行管理，从而保证范围、进度、配置三类计划相互一致、形成闭环。

## 3. 进度安排依据

### 3.1 关键路径选择

### 3.2 责任人分配

## 5. 冲突解决过程记录

### 5.1 冲突制造场景设计
配置管理文档（§2.1）已经规定了"feature → dev → main"的合并流程，但项目经理在内部讨论时提出能否直接将 feature 合并到 main 以缩短验证链路。两种意见均合理，因此本组通过 Git 实际合并冲突方式作为决策依据。具体场景设计写在 `docs/conflict.md`：朱默涵与刘瑞祥分别在 `feature-conflict-zhu`、`feature-conflict-liu` 两条分支上对同一行"当前结论"做出不同修改。

### 5.2 冲突制造与识别
- **2026-05-07 10:00**，朱默涵在 `feature-conflict-zhu` 上将"当前结论"改为倾向直接合并到 main 的表述并提交。
- **2026-05-07 10:30**，刘瑞祥在 `feature-conflict-liu` 上将"当前结论"改为倾向"feature → dev → main"标准流的表述并提交。
- **2026-05-07 11:00**，配置管理员杜航屹在 `dev` 分支上先把 `feature-conflict-zhu` 通过 `--no-ff` 合并入 `dev`（无冲突）。
- **2026-05-07 15:30**，再尝试合并 `feature-conflict-liu` 时 Git 报告：

```
Auto-merging docs/conflict.md
CONFLICT (content): Merge conflict in docs/conflict.md
Automatic merge failed; fix conflicts and then commit the result.
```

通过 `git status` 与文件中的 `<<<<<<< HEAD` / `=======` / `>>>>>>> feature-conflict-liu` 标记，迅速定位到冲突行。

### 5.3 冲突解决与最终结论
全组在群里讨论 5 分钟后达成一致：

1. 配置管理文档已经写明"feature 必须先合并到 dev"，应当遵守已生效的约定，不能因临时讨论就推翻。
2. 直接合并到 main 会丢失 dev 的集成验证环节，对里程碑控制不利。
3. 最终保留刘瑞祥的方向并稍作润色：所有 feature 分支必须先合并到 `dev`，由项目经理按里程碑节奏将 `dev` 合并到 `main`；禁止 feature 直接合并到 main。

刘瑞祥在工作目录中删除冲突标记并写入合并后的"当前结论"行，朱默涵确认表述无歧义后由配置管理员执行 `git add docs/conflict.md && git commit` 完成合并提交。配置管理员复核合并提交保留两条父提交（`feature-conflict-zhu` 与 `feature-conflict-liu`），可通过 `git log --graph` 直接查看。

### 5.4 冲突过程留痕
冲突文件、冲突原因、处理方式、最终结论与复核人已在 `docs/conflict.md` §5 中追加记录；本报告 §5 与之内容一致，保证仓库中所有冲突相关内容都互相对照、便于核查。

## 6. 经验与问题

### 6.1 主要经验

1. **WBS 必须由交付物驱动**：在初稿阶段计划负责人差点把"开会讨论"当作 L3 条目，复核后改为对应的成果文件，进度计划与配置管理才能围绕同一组成果展开闭环。
2. **分支策略要先讲清再开干**：配置管理文档先于多数 feature 分支完成，避免了"分支名乱起、合并方向不清"的问题，使后续四个 feature 分支的合并节奏稳定。
3. **冲突演练应当有真实场景**：本组没有人为编造冲突，而是借助"是否绕过 dev"这一真实意见分歧来设计 `feature-conflict-zhu` 与 `feature-conflict-liu`，冲突解决讨论也直接产出了对配置管理文档的反向印证。
4. **提交粒度与说明同样重要**：所有提交均使用 `init/docs/fix/merge/chore` 前缀和动宾结构中文说明，使得 `git log --oneline` 能直接当作过程记录查阅。

### 6.2 主要问题与改进方向

1. **业务设计文档详尽度不足**：WBS 2.x 给出了业务设计文档的成果点，但本次实验为聚焦项目管理过程，仅保留了字段级描述，缺乏完整原型；后续如需扩展，应在 dev 分支上单独切 `feature-business` 补齐。
2. **远端推送频率较低**：本组多数提交在本地完成，到 M3、M5 节点才统一推送 GitHub；若有外部评审介入，应至少每个 feature 合并到 dev 后立即推送，便于评审人随时查看。
3. **手工冲突解决依赖经验**：第一次冲突演练时仍有成员对 `<<<<<<<` / `=======` / `>>>>>>>` 标记不熟悉；后续可在 CONTRIBUTING.md 中追加截图或动图，降低新成员的学习门槛。

### 6.3 实验收获总结
通过本次综合实验，组员系统体验了"范围 → 进度 → 配置 → 协作 → 收尾"的项目管理闭环，理解了 WBS、关键路径、配置项、分支策略、冲突解决在真实仓库中如何相互联系。所有最终成果（包括本报告）均已在解决冲突后合并到 `main` 分支，并打 Tag `v1.0` 作为最终基线。
