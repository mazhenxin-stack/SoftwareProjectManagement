## 2. WBS 分解思路

### 2.1 一级条目划分理由
本组将项目交付物划分为 4 个一级条目：项目管理成果、业务功能成果（设计文档）、协作过程成果、总结与归档成果。这 4 个一级条目分别对应"过程受控"、"范围覆盖"、"协作能力"和"实验收尾"四个维度，能够把指导书与题目说明书提出的全部要求映射到具体成果上。

### 2.2 三级分解原则
分解中坚持三条原则：

1. **结果导向**：每条 L3 条目都是一项可识别、可交付、可验收的成果，避免使用"开会、讨论、修改"等纯动作型语言。例如 1.2.2 直接对应 `docs/03-schedule.md` 文件，而不是"做进度计划"动作。
2. **范围完整覆盖**：将题目说明书中明确的"活动管理 / 报名管理 / 签到管理 / 统计与导出"4 类业务一一映射到 2.1–2.4 子树，避免漏项；同时把指导书中提到的协作过程成果落到 3.x，把总结归档落到 4.x，与实验报告章节直接对应。
3. **可独立分配**：L3 条目以"一人一日内可完成"为粒度参考，例如 2.1.1 活动信息字段说明与 2.1.2 活动发布页面草案分开作为两条 L3，便于在进度计划中独立排期与分配。

### 2.3 与进度计划、配置管理的对应
WBS 中每条 L3 都在 `docs/03-schedule.md` 的"对应 WBS 成果"列中被明确引用，并在 `docs/04-config-plan.md` §1 的配置项清单中作为受控对象进行管理，从而保证范围、进度、配置三类计划相互一致、形成闭环。

## 3. 进度安排依据

### 3.1 关键路径选择
关键路径为 A1（仓库初始化）→ A2（项目章程）→ A3（WBS）→ A4（进度计划）→ A11（总结报告主体）→ A12（评审）→ A13（dev → main 合并）。这条路径串起了从仓库建立到最终合并的最长依赖链，决定了实验的总体周期。其他活动（A5 配置管理、A6 业务设计文档、A7–A10 协作与冲突）均与关键路径并行排布。

### 3.2 责任人分配
进度安排在分配责任人时遵循"角色对应交付物"原则：项目章程归项目经理，WBS 与进度计划归计划负责人，配置管理归配置管理员，协作完善与冲突解决归协作成员。每个 L3 条目被映射到一个主责任人，以便后续追踪个人贡献。同时四人在工作量上均控制在约 1.5 人 · 天，配置管理员的合并工作作为常态职责另行承担，确保对外可见的内容产出基本均衡。

### 3.3 缓冲与风险预案
A12（评审）与 A13（合并到 main）各占 0.25 天，整体计划预留 0.5 天的 buffer 以应对：

- 总结报告评审反馈的多轮修改；
- 远端推送权限或网络问题导致 main 合并延后；
- 冲突演练失败后的二次设计与执行。

风险与对应应对策略已写入 `docs/03-schedule.md` §6。
